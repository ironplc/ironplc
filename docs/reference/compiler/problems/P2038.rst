=====
P2038
=====

.. problem-summary:: P2038

This error occurs when a date literal names a date the compiler cannot
represent.

A date is stored as a count of seconds since 1970-01-01, and the count is
unsigned, so the dates a program can write are the ones that count reaches:

.. list-table:: Date type ranges
   :header-rows: 1
   :stub-columns: 1

   * - Type
     - Earliest
     - Latest
   * - **DATE**, **LDATE**
     - ``1970-01-01``
     - ``2106-02-07``
   * - **DATE_AND_TIME**, **LDATE_AND_TIME**
     - ``1970-01-01-00:00:00``
     - ``2106-02-07-06:28:15``

A date outside that range has no second count to be stored as, so the compiler
reports it rather than storing a different date than the one the program wrote.

Example
-------

The following code will generate error P2038:

.. code-block::

   PROGRAM main
       VAR
           expiry : DATE := DATE#2200-01-01;
       END_VAR
   END_PROGRAM

To fix this error, use a date the type can hold:

.. code-block::

   PROGRAM main
       VAR
           expiry : DATE := DATE#2099-12-31;
       END_VAR
   END_PROGRAM

Dates before 1970
-----------------

The count of seconds is unsigned, so it has nowhere to put a date before the
epoch. A historical date is reported for the same reason a distant future one
is:

.. code-block::

   PROGRAM main
       VAR
           built : DATE := DATE#1969-07-20;  (* Error: before 1970-01-01 *)
       END_VAR
   END_PROGRAM

Where a program needs to record a date outside the range, store the offset
from a date inside it — days or seconds in an integer variable — rather than
the date itself.

The 64-bit types have the same range
------------------------------------

``LDATE`` and ``LDATE_AND_TIME`` are wider in storage than ``DATE`` and
``DATE_AND_TIME``, but they hold the same count of seconds, and the compiler
computes that count the same way for all four. So an ``LDATE`` literal reaches
no further than a ``DATE`` literal, and ``LDATE#2200-01-01`` is reported
exactly as ``DATE#2200-01-01`` is.
