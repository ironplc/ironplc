# Compile bit and partial access through one path in codegen (#2053)

## Goal

Compile a bit access (`x.3`, `x.%X3`) and a partial access (`x.%B1`) through
one path in `compiler/codegen`, as #2053 asks. A bit access is the one-bit case
of a partial access: `bits` bits starting at bit `shift`. One abstraction
addresses the place the bits live in, one function reads the bits, and one
writes them. Reads and writes address the base the same way.

Generated bytecode stays identical for every program that codegen compiles
correctly today. That covers every existing test, and every existing
end-to-end test passes unchanged.

## Today

Measured on `main` at 0dc073a.

- **Writes.** Eight functions in `compile_expr.rs`, lines 1007–1547: one per
  access kind (bit, partial) and base shape (variable, array element, structure
  field, element of an array in a structure). Their helpers add another 110
  lines: `emit_partial_access_read_modify_write`, `low_bits_mask`,
  `partial_access_on_float`, and the `extract_*_target` functions. Each one
  addresses its base with its own code: `resolve_symbolic_variable_name` and
  an `array_vars` lookup, `resolve_struct_field_access`, or
  `resolve_struct_field_array`. The bit-access functions repeat the same
  clear, mask, shift, OR sequence inline, once per shape and width.
- **Reads.** Two arms of `compile_variable_read`, lines 608–737. Each has its
  own copy of the `match` that works out the base's width, followed by
  a recursive `compile_variable_read` of the base, which addresses it through
  `resolve_access`.

So reads and writes do not share addressing, and they accept different bases.
Each row below was checked with `ironplcc compile` and `ironplcvm run`:

| Base | Read today | Write today |
|---|---|---|
| variable, array element, structure field, element of an array in a structure (`s.arr[i]`) | correct | correct |
| `VAR_IN_OUT` parameter | correct | P9999: `var_index` refuses an in-out name |
| element through a `REF_TO ARRAY` (`p^[i]`) | correct | `LOAD_ARRAY` on the reference: V9008 at run time |
| field of an element of an array of structures (`a[i].f`) | P9999 | P9999 |
| element of an array field of such an element (`a[i].vals[j]`) | at 32 bits: bit 40 of an `LWORD` element reads `FALSE` | P9999 |
| bits of bits (`d.%B1.3`) | correct | writes bit 3 of `d` |
| through a reference (`p^.3`) | P9999 | writes into `p` itself |
| a `STRING` variable | operates on the string's buffer index | operates on the variable's slot |

## Architecture

### Addressing a place

A new module, `compile_place.rs`, holds `Place`: a place that holds one value
in a single slot.

- `Place::resolve(ctx, base)` takes the base's `SymbolicVariableKind`. It
  builds on the two resolvers ordinary reads and assignments already use:
  - `resolve_struct_field_access` for a field at a fixed offset;
  - `resolve_access` for everything else.
- It has three addresses:
  - a variable (`LOAD_VAR`/`STORE_VAR`);
  - a `VAR_IN_OUT` parameter (`LOAD_INDIRECT`/`STORE_INDIRECT` through the
    reference);
  - an element of a slot array. The index is either a fixed slot, for a
    structure field, or the flat index of the subscripts, plus the array's
    slot offset when the array is part of a structure. The opcodes are
    `LOAD_ARRAY`/`STORE_ARRAY`, or their `_DEREF` forms through a reference.
  `ResolvedAccess` already gives every one of these except the fixed-offset
  structure field, which the read and assignment paths special-case before
  calling it.
- A `STRING`, a `STRING` array element, a bits-of-bits base and a
  dereferenced scalar (`p^`) are not places, so they are reported as P9999.
- `emit_load` pushes the value. `emit_store` truncates the value to the
  place's type, then stores it.
- `emit_store` emits the address again rather than reusing the one
  `emit_load` computed. A subscript with a side effect is therefore still
  evaluated twice, which #2053 says to keep. Evaluating it once later only
  changes `Place`.
- `resolve_access` takes a `&Variable`, but a bit access's base is a
  `Box<SymbolicVariableKind>`; the read path clones it into a `Variable` today.
  A new `resolve_symbolic_access` takes the `SymbolicVariableKind`, and
  `resolve_access` delegates to it.

### Reading and writing the bits

A new module, `compile_partial_access.rs`, holds `PartialAccess { base, bits,
shift, span }`, built from either AST node (`bits` is 1 for a bit access).

- `compile_partial_access_read` resolves the base's `Place`, loads it, shifts
  the bits down to bit 0 and masks them. `compile_variable_read` calls it for
  both nodes.
- `compile_partial_access_assignment` loads the place, clears the bits,
  compiles the value, masks it, shifts it into position and ORs it in, then
  stores the place. `compile_stmt.rs` calls it for both nodes.
- The value written is compiled as `BOOL` for one bit and as the bit string as
  wide as the selection otherwise. That reproduces both of today's rules: the
  bit-access functions used `DEFAULT_OP_TYPE`, which is `BOOL`'s, and the
  partial-access ones used the slice's width.
- A bits-of-bits read (`d.%B1.3`) reads its base as a value, at 32 bits, as
  today. It has no place to write to, so that write becomes P9999.

### Keeping the bytecode identical

Bit and partial access differ in two ways today. Each difference is kept as
one documented line in `PartialAccess`, so each can be removed in its own
change:

1. **Shift by zero.** A bit access emits `LOAD_CONST 0; SHL`/`SHR`; a partial
   access skips it. Existing tests write `x.0`, so dropping it would change
   their bytecode. Kept by `shifts()`.
2. **Floating-point base.** A partial access of a `REAL` or `LREAL` is
   refused; a bit access compiles at 32 bits. That is the `REAL`'s IEEE bit
   pattern, but an `LREAL` loses its high half: `r.0 := TRUE` on 1.5 leaves
   5e-324. Kept by `integer_width()`. It goes once analysis rejects the access
   (#1851, #1911).

**How it was checked.** A prototype of PR 3 was compared with `main` using a
temporary hook, not committed, in the codegen test harness's
`try_parse_and_compile`. The hook wrote the container bytes of every program
the codegen suite compiles: 676 programs.

- A further 161-program corpus covered:
  - each access (`.n`, `.%Xn`, `.%B`/`%W`/`%D`/`%L`) on every base shape above
    that compiles today, at 8 to 64 bits;
  - values written as literals, variables and expressions;
  - subscripts that are constant, computed, or a function call;
  - `REAL` and `LREAL` bases, bits-of-bits reads and `VAR_IN_OUT` reads;
  - accesses in function block bodies, on `VAR_GLOBAL`s and on function
    locals.
- Every compiled program's bytes were identical before and after, with one
  exception. A program declaring two enumeration types changes between runs on
  `main` too: its type section is ordered nondeterministically.
- The only other differences are error messages. A function's local array is
  not supported, and its bit access now reports the error a plain read of it
  reports.

### Behaviour that changes

Only for the bases where reads and writes disagree today. Each now follows the
addressing reads use:

| Base | After |
|---|---|
| `VAR_IN_OUT` parameter, write | correct |
| `p^[i]`, write | correct |
| `a[i].f`, read and write | correct |
| `a[i].vals[j]`, write; read of a 64-bit element | correct |
| `d.%B1.3`, write | P9999 |
| `p^.3`, write | P9999, as the read already is |
| `STRING` base | P9999 |

These changes come from having one addressing path. They cannot be split out
without adding code that reproduces the old wrong results, so PR 3 lands them
with a test each (Decision 1).

## Prefactoring

The whole change is a prefactor: #2053 is one of the `lowering-pre-factor`
issues, so that lowering (#2011) translates one path instead of eight. It is
delivered as three PRs, each from `main`:

1. **Tests.** An `rstest` matrix in a new
   `end_to_end_partial_access_bases.rs` covers every combination of:
   - access: bit, `%X`, `%B`, `%W`, `%D`, `%L`;
   - base: variable, array element, structure field, element of an array in
     a structure;
   - width: 32 and 64 bits;
   - operation: read and write.
   It passes on `main`: 104 cases. It pins today's results before the
   restructure. It replaces nothing; the existing tests stay as they are.
2. **`resolve_symbolic_access`.** `resolve_access` delegates to a version that
   takes a `SymbolicVariableKind`, and `DimensionInfo` derives `Clone`. No
   behaviour change.
3. **One path.** Add `Place` and `PartialAccess`, and delete the eight
   functions, their helpers, the two read arms and
   `resolve_symbolic_variable_name`, which nothing else uses. Then:
   - add the array-of-structures base to the matrix (26 more cases);
   - add a test for each other row of "Behaviour that changes";
   - update the design document.

## Design doc reference

- `specs/design/partial-access-bit-syntax.md`. Its overview says a partial
  access has "its own AST node and codegen path". After PR 3 it has its own
  AST node, and codegen compiles it through the same path as a bit access.
- REQ-PAB-codegen-132 ("reads and writes of a slice work on array elements and
  structured fields") gains the matrix as a test in PR 1. PR 3 widens it to
  elements of arrays in structures, fields of structures in arrays, and
  `VAR_IN_OUT` parameters.
- The lowering design on #2011 is not on `main`, so neither code nor docs cite
  it.

## Decisions for review

1. **Behaviour changes in PR 3.** Land the changes listed under "Behaviour
   that changes" in PR 3, with tests (recommended), rather than adding code
   that keeps the old results until a later PR.
2. **The two bytecode differences.** Keep both in PR 3, so the bytecode stays
   identical as #2053 requires (recommended). They become follow-up issues:
   dropping the zero shift is a one-line change, and refusing a float base for
   bit access waits on #1911.
3. **PR 2 separate from PR 3.** Recommended, so that PR 3's diff is only the
   restructure. It is 25 lines and could fold into PR 3 if preferred.
