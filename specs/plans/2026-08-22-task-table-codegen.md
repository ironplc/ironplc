# Emit the Task Table from Codegen

## Goal

Carry `TASK ... (INTERVAL := ..., PRIORITY := ...)` from the source program
through to the bytecode container's task table, so the VM schedules the program
at its configured rate instead of free-running.

## Background

`compile` reads the `CONFIGURATION` only for `global_var`
(`codegen/src/compile.rs:221-222`). Nothing in `codegen/src` constructs a
`TaskEntry`, so every container falls through to `ContainerBuilder::build`'s
synthesized default (`container/src/builder.rs:332-360`): one task,
`TaskType::Freewheeling`, `interval_us: 0`, `priority: 0`.

The parser already produces the values (`parser/src/parser.rs:1607-1621`) and the
DSL carries them (`dsl/src/configuration.rs:141-150`) — they are dropped at
codegen.

Consequences today:

- `TaskScheduler::collect_ready_tasks` always takes the `Freewheeling => true`
  branch (`vm/src/scheduler.rs:59`), so `record_execution` never re-arms anything.
- `VmRunning::next_due_us()` always returns `None`, so `ironplcvm`'s sleep
  (`vm-cli/src/cli.rs:86-92`) never runs and the runner spins free.
- The debugger cannot honor an interval that is not in the container, which is
  what blocks issue #1397.

## Architecture

`compile_program_with_functions` returns a finished `Container`, and
`Container.task_table` is public. Rather than thread task data through the
builder, apply the configuration to the finished container — the same shape as
the existing `container.header.flags |= FLAG_HAS_SYSTEM_UPTIME` at
`compile.rs:289-291`.

The VM is single-instance in v1, and `find_program` compiles exactly one
`PROGRAM`, so the table keeps one task and one program instance. Only the task
entry's fields change. `TaskTable::section_size` is computed at write time and
does not depend on the task type, so no offsets move.

### Binding

`ConfigurationDeclaration.resource_decl[*].programs` holds `ProgramConfiguration`
entries; each has `type_name` (the `PROGRAM` type it instantiates) and
`task_name` (the `TASK` it runs under). Resolution:

1. Find the `ProgramConfiguration` whose `type_name` matches the compiled
   program's name (`Id` compares case-insensitively).
2. If it names a task, look that task up in the same resource's `tasks`.
3. Anything not found — no `CONFIGURATION`, no matching program config, no
   `task_name` — leaves the synthesized freewheeling default in place.

### Mapping

| Source | `TaskEntry` |
|---|---|
| `INTERVAL := T#100ms` | `task_type: Cyclic`, `interval_us: 100_000` |
| no `INTERVAL` | `task_type: Freewheeling`, `interval_us: 0` |
| `INTERVAL := T#0ms` | `Freewheeling` — a zero interval means "as fast as possible", and a `Cyclic` task with `interval_us: 0` would be permanently overdue and inflate `overrun_count` every round |
| `PRIORITY := n` | `priority: n as u16`; `n > u16::MAX` is a diagnostic |
| `SINGLE := var` | diagnostic — see below |
| — | `watchdog_us: 0` (no DSL surface yet) |

### Rejecting SINGLE

`TaskType::Event` is stubbed `false` in `collect_ready_tasks`
(`vm/src/scheduler.rs:62`), so an event task would compile to a program whose
task never runs. Codegen reports a diagnostic instead of emitting one.

## Not in Scope

Multiple tasks or multiple program instances per container (the VM is
single-instance in v1); `TaskType::Event` execution; `watchdog_us`; the debugger
clock (issue #1397, follow-up PR); defaulting the Playground's interval box from
the program.
